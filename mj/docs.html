Control flow

if / else

if (cond) {
  ...
} else if (cond) {
  ...
} else {
  ...
}

Compiles to: evaluate the condition, OP_JUMP_IF_FALSE into the else branch, the then body, an unconditional OP_JUMP past the else, then the else body.

while

while (cond) {
  ...
}

for (C-style)

for (init; cond; step) {
  body
}

Desugars to:

{
  init;
  while (cond) {
    body;
    step;
  }
}

Labels and goto

start:
  ...
  goto start;
  ...
  if (x > 10) goto done;
done:

name: defines a label at the current bytecode offset. goto name; emits OP_JUMP (or OP_LOOP for a backward jump) and patches the offset.

Conditional jumps

Used internally, and exposed: OP_JUMP_IF_FALSE, OP_JUMP_IF_TRUE (optional), OP_JUMP (unconditional).

The template JIT turns all of the above into native jcc / jmp instructions with correct rel32 patching.

Error handling

Compile-time

Format: file:line:col: error: message. Shows the source line with a caret under the column, plus near-token context when useful.

Runtime

Format: file:line: runtime error: message. Includes a call stack of function names, with typed hints by error class:

  • division / modulo by zero
  • non-callable values
  • index out of bounds (reports index and length)
  • wrong index key types (array needs a number, map needs a string)
  • stack / frame overflow (recursion)
  • C-interop arity / type / null pointer

Catch (fixed 2026-08-17)

If a catch handler is active, runtime errors jump there, the same path as panic, instead of exiting immediately. A parsing bug that limited catch(err) { ... } bodies to a single trailing expression has been fixed -- bodies now accept ordinary statements (print, var, and so on), with the last stacked value used as the recovery result.

var x = 1 / 0 catch(err) {
  print err;
  0;
};

Import path resolution and import-time error reporting were also tightened up in the same update.

Safety goal

A clear abort is preferred over a silent segfault. Bounds and type checks sit on the slow path (__builtin_expect), so hot numeric loops stay tight.

GC and ownership

Does GC affect speed

Yes, when it runs. Pure numeric JIT loops allocate nothing, so the impact is close to zero. Allocation-heavy code may pause near 75 percent of the 512MB arena.

./mj --no-gc script.mj

Is GC safe

Optional mark-sweep is safe to enable. The bump allocator does not free individual objects yet; marks support a future free-list. Use --no-gc for maximum determinism.

Ownership

--ownership is experimental and off by default. Full borrow checking is not enforced yet.

Optimizations

Modern bytecode techniques, aimed at script makers and hobby programmers: fast enough to be fun, simple enough to understand and control.

Compile-time passes -- optimize()

  1. Constant folding -- CONST a; CONST b; ADD/SUB/MUL/DIV/MOD/CMP collapses to a single CONST result. Unary NEG / NOT on constants is folded too.
  2. Dead code elimination -- marks jump targets and sequential flow, drops unreachable code after RETURN and unconditional JUMP.
  3. Superinstructions -- s = s + i becomes OP_ADD_LOCALS; i = i + 1 becomes OP_INC_LOCAL. Jump offsets are retargeted after compaction. New as of 2026-08-17, where present: OP_ADD_LOCAL_CONST and OP_MUL_LOCAL_CONST for local += const / local *= const.
  4. NOP elimination -- folded and dead instructions are removed, code is compacted.
  5. SSA / register hints -- new pass feeding the template JIT on numeric windows.

Runtime

  • Stable frame pointer, no per-instruction frame reload
  • Dense numeric locals for fused ops
  • OP_SUM_LOOP / OP_SUM_GLOB_LOOP for hot loops
  • Optional MJ_DUMP=1 to inspect bytecode after optimization

Design note, versus LuaJIT

LuaJIT uses a tracing JIT and SSA-style IR. mj stays a small, readable bytecode VM with a template-JIT heritage, so the kernel remains under complete control in one C file. The passes above chase the same ideas, folding, DCE, specializing hot patterns, without the complexity of a full trace compiler.

Data management, near-native

  • Dense numeric arrays: a parallel int64_t nums[] buffer when every element is a number
  • range(n) / range(lo, hi), built in C
  • array_sum / array_min / array_max, C loops over the dense buffer
  • array_fill(n, v) / array_copy, bulk operations in C
  • sum_range(n), a native 0..n-1 sum, same speed as a fused while loop
  • array(cap), pre-sized capacity to avoid repeated growth
  • A larger heap, 512MB, for big working sets

Bytecode and .bbw inspection

Commands

# Pretty-print compiled bytecode for a source file (includes nested funs)
./build/mj --disasm path/to/script.mj

# Inspect a shipped .bbw bundle (plus a raw hex dump)
./build/mj --disasm path/to/script.bbw
./build/mj --dump-bbw path/to/script.bbw   # same

Output

  1. Header -- name, code length, nlocals, nconst, arity, upvalues
  2. Constants pool -- numbers, strings, function refs
  3. Code listing -- offset OPCODE operands ; comments
  4. For .bbw only -- a raw code hex dump, for reverse engineering

Notes

  • .bbw v1 stores the top-level script only; nested fun bodies may appear as nil in the const pool when loading a .bbw (compile from .mj with --disasm to see full nested functions)
  • Jump operands show absolute target offsets, e.g. -> 00ab
  • Specialized ops (SUM_LOOP, ADD_LOCALS, ...) print structured operands

Example

0010  SUM_LOOP           acc=L[2] idx=L[3] lim=L[1]
0009  CALL               argc=1
0000  CONST              1       ; 10
